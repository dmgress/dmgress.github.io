I recently wrote about CloudGrapher, my personal project aimed at grasping the big picture from AWS CloudFormation templates. Although it's great it exists, I didn't mention all the frustration and struggle I have been going through. For documentation and entertainment purposes, let's see what stumped and amazed me.

First of all, because CloudGrapher is written in JavaScript and I wanted to familiarize myself with the Gulp build tool/system/magic I was bound to hit some annoyances. Coming from a Java background where Maven rules and everything is static, the plunge into the handwavey trickster world of JavaScript can be a challenge. In my opinion the basics of JavaScript are easy enough for mortals to understand, but you'll hit the swamp of smelly code generated by copy-paste trolls soon enough.

## Dependency management

I started CloudGrapher knowing that get dependencies right in JavaScript over infinite time is hard. Libraries get updated fast, they get outdated fast. Today's best way is tommorow's dead-end road. APIs change, projects stop being maintained.

Because my application is intended for a browser all of my NPM dependencies are for development. The dependencies the application uses are defined in Bower. Bower is decent enough, it saves me from downloading and maintaining my dependencies. However, there is an uncertainty that building the project tomorrow might give a different result if you can't lock down Bower dependencies sufficiently. Yes, that's another thing you might to think about. There is nothing more frustrating when developing hotfixes on inactive projects than dependencies being so liberal in versioning that it can result in your next build hitting an API break.

This is where automated testing comes it. Automated builds testing on changes, but in case of projects that aren't actively developed also periodic builds. The periodic builds will most likely catch breaking APIs if test coverage is sufficient enough to find them.

## Bad wizard, bad!

For a novice the best way to start with Gulp seems to be some wizard that will setup your project structure. Sadly, most of the time it's not the structure I would like and you can be quite sure the gulpfile.js contains (outdated) magic. If you use a wizard to start, it's fine as long as you don't expect it to support the latest version of all the tooling it generates for you. I started out with a wizard. The setup was fast. I did an update. Everything broke and JavaScript stack traces can be just as insane as the ones Java generates. Although, once you sort of get how it's build up then it's not so insane.

TIP, if start with a wizard then that's fine. It will get you started fast, it will get you stuck if you don't understand what it generates.

Once you get several JavaScript projects, you will either generate your own wizard which will use an outdated stack or find your own way to ideally bootstrap your projects. This is much better than trusting any grunt, gulp or yeoman wizard to do the right thing for now.

What did I do to solve it? I did what any novice would do. Copy paste something that does work. Even the pros do this, it's no shame to copy, just a shame if you don't understand what it does. The next evolution is to look at the code of others, understand it, apply it to what your mental state says is best for you. There might still be some legacy dependencies or weird gulp tasks left in my gulpfile.js but at least I understand what they do and the painful road to understanding them edged that understanding into long term memory. These horrors do not fade...

## Don't tell me what I need

From my stance point as a support and infrastructure aware software developer it's really annoying to see for instance a .htaccess generating plugin. Why? Because it gives a false security that part is sufficiently covered. It could be, but more likely it isn't because now most people won't bother trying to understand it.

## Adding tests / Why you should be testing stuff

Everything starts with good intentions, but it's far too common to make a mess while hacking away at source code. Except for the savant geniuses blessed with quantum-vision into every code point most of us will at some point get groggy, frustrated and probably fudge the good guides and manners they usually have. One way to combat this is with sufficient testing.

TDD, BDD, happy flow testing or click monkeys from cheapo land, any is better than not testing at all. Why? Because it only takes a flash to instill the uncertainty that changing the code might break the system. Again, some fearless savant won't care because everything still fits in his brain, but without testing you will often see another annoying thing which is called by many names but usually summarized as a waste of resources: the standard output or error print out.

Once I passed the hacking phase, I started with some basic unit testing. In this case the testing of the code to translated the CloudFormation into a graph understandable by the graphing framework (cytoscape.js).

## Continuous Integration

Travis CI is what I chose as continuous integration option. I used it before and it looks simple enough to start with.

## Code coverage / static analyses

Continuous integration is not just getting feedback on tests, but also on general code and test value. To get a good view of my current status I decided to add several code metrics services to my development pipeline.

### CodeCov

Another integration from the GitHub integrations page is CodeCov. At the time of writing it was kind of magic, because I didn't bother understanding how to run it locally. It seems to do some environment analysis and adjusts it's behaviour according. Sadly there is no behaviour for working normal in Cloud9 and I suspect local system. So after some trial and error I figured out a working setup. Don't remember if official documentation or reading the code from GitHub repo got me to my answer.

### Code Climate

Most of the configuration for this integration I got from a blog post titled [Better Javascript with Gulp, Mocha, Istanbul and Codeclimate](http://blog.oskoui-oskoui.com/?p=8478). My stack doesn't include Mocha, I'm using Jasmine instead, afterwards the difference isn't so big. Again, I stumbled on 1) the fact that there are many ways to do things in JavaScript and Gulp, 2) the recommended way of doing this is best obtained from the actual tooling page itself. In this case the flow has the following dependencies:

* Gulp -- obviously
* Istanbul (more specifically gulp-istanbul), to generate LCOV data
* Your testing framework, in my case this is Jasmine through gulp-jasmine
* Code Climate, free if your repository is public on GitHub and you consider it open source. Otherwise the pricing starts quite high for just a pet project
* codeclimate-test-reporter npm module to feed data to codeclimate

Code Climate uses a repository unique token. That means somehow you need to have it available as environment variable. The gist is that you instrument all your custom JavaScript code, Tell istanbul to write the reports, feed the `lcov.info` to Code Climate.

### Codacy

As I mentioned, the lowest tier for Code Climate is quite a high barrier for a pet project from my perspective. If it wasn't for the free analysis of OSS, then I would have probably not consider it and opted for manual on-demand analysis of what it offers. Codacy is one of the alternatives. Again, free on OSS which I guess means they get some other data from analysis my open source code which they can sell on to third parties. Library usage or programming language stuff.

Tin foil head moment, be sure to keep personal identifiable info and secrets out of your repos!

Codacy's pricing starts at a lower level. Clearly their demographic caters more to single user accounts whereas Code Climate tends to target organizations.

Codacy does most of the analysis on it's own as it hooks into GitHub and triggers on pushes. It's easy to add coverage data into Codacy too, because after installing `codacy-coverage` you feed it the LCOV file and supply it the correct token.

## Enlightened UI

I spent more time on tying together the user interface and fixing CSS! I'm not really into pixel-perfect nice user experience with beautiful graphics. In most of the work I do professionally it's supposed to work, looking good is not that important. So I started out with a framework for layout and an editor framework that both turned out to be overkill and quite heavy on the initial load. It's easy to forget that not everybody has high-speed internet everywhere on all devices and I learned from humbling experience how frustrating it can be to be on a slow network when everybody expects their application to be nearly as fast running from the web as running locally. So I ended up ripping those out and going fairly light and low-level on web design. I learned that HTML5 and CSS3 can really make it easy to get fancy without huge page sizes. In the future I intend to trim CloudGrapher even more, both in size and number of initial requests.

## Lessons learned

The best way for me to learn is to immerse myself into the technology. Walk a few circles around the pool, figure out where to jump in with a deep dive. It will get messy and it will be hard, but experience and horrors from the past allow me to cut my way through the dense minded inhabitants and heavily forested jungle of JavaScript and setting stuff up properly. You shouldn't assume the training wheels you get from a wizard will last long. Get into understanding what that wizard did, demystify the magic and get it into something that seems more sane to you.
